## Domain
Claim (market, type, amounts, currency, status, assigned officer, version), ClaimStatusHistory (audit trail), ClaimInfoRequest (officer question / claimant response).
Lifecycle: SUBMITTED → UNDER_REVIEW ⇄ INFO_REQUESTED → ASSESSED → APPROVED / REJECTED → SETTLED. Transitions are enforced in one place (`ClaimStatus` / `Claim.changeStatus`), and every change writes a history row in the same transaction.

## Key decisions
- **Modular monolith, one service.** One team, one database and a 3-hour budget; splitting would add network and deployment overhead with no benefit. Natural future seams: notifications, reporting/exposure projection, auth.
- **REST for everything today.** Submitting, assigning and deciding claims need an immediate, consistent response. I did not add Kafka: with one service and one DB there are no independent consumers yet. It becomes worthwhile when notifications, reporting and audit consume claim events separately, need replay, or must scale independently across six markets. The plan is domain events behind an interface, published through a transactional outbox, with idempotent consumers.
- **PostgreSQL + Flyway**, with `ddl-auto=validate` so migrations own the schema and Hibernate only checks it.
- **Optimistic locking (`@Version`)** for concurrent pick-up, so two officers can't take the same claim: one gets 409.
- **Exposure** = reserve if assessed, otherwise claimed amount, for all non-terminal claims, grouped by market and currency, never summed across currencies (FX conversion is out of scope).
- **Security:** stateless JWT with CLAIMANT / OFFICER / MANAGER roles, URL rules plus service-layer ownership checks (other claimants' claims return 404). Identity comes from the token, never the request body.
- **API contract:** DTOs (Java records) separate from entities; RFC 7807 `ProblemDetail` error format; OpenAPI generated by springdoc.

## Shortcuts taken (time-boxed)
Hardcoded demo users and a shared HMAC secret with a dev default; no refresh tokens or revocation; no document uploads; no real notifications; no integration test suite; no FX conversion; manager approval limits not modelled.

## What I would do next
1. Testcontainers integration tests, especially the concurrent pick-up race.
2. Transactional outbox + Kafka for claim events (notifications, exposure projection, audit).
3. External IdP (OIDC) with RS256 and JWKS instead of the demo user directory.
4. Authority limits (manager approval above a reserve threshold) and SLA/ageing alerts.
5. Document attachments, pagination/sorting options, optimistic-lock retry UX, metrics and tracing.
